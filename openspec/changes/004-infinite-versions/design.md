# Design

## Context

Поточна архітектура (`pipeline.py`, `worker.py`, `src/studio-controller.ts`, `src/main.ts`) побудована навколо моделі «1 оригінал + 1 плоский файл результату `output/<stem>.<ext>`»:
- `StudioPipeline.find_output_file(stem)` шукає єдиний файл у корені `output/`.
- `_save_output_image()` перезаписує `output/<stem>.<ext>` і видаляє файли того ж `stem` із іншими розширеннями.
- `StudioController.getFileVersions()` конструює фіксований масив із 1 або 2 елементів (`original`, `output`), а `takeVersionIntoWork(filename, 'original')` фактично викликає `restoreSingle()`, знищуючи результат.
- Потрібно перейти до нескінченної історії проміжних версій без зміни безпекових інваріантів JetPack (див. `proposal.md` та delta-специфікації `image-pipeline-worker` і `studio-web-ui`).

## Goals / Non-Goals

**Goals:**
- Зберігати кожен результат обробки в окремій підпапці файлу: `output/<stem>/<stem>-v<NNN>.<ext>` (наприклад, `output/my-image-1/my-image-1-v001.jpg`) з монотонною нумерацією `001`, `002`, ….
- Персистентно зберігати обрану активну версію для кожного файлу (`original` або `vNNN`), щоб продовжувати роботу, показувати прев'ю/слайдер/мінімапу та запускати наступну операцію саме від обраної версії.
- Підтримувати перегляд, скачування та видалення будь-якої проміжної версії через бічний `#version-popup`.
- Забезпечити багатокроковий стек `Undo` у воркері (`studio.undo`) та іконкову кнопку `Undo` на лівій панелі керування поруч із `Process` / `Process All`, із фізичним видаленням створених файлів при скасуванні.
- Експортувати всі збережені версії у `studio.download_zip` зі структурою `<stem>/<stem>-vNNN.<ext>`.

**Non-Goals:**
- Міграція застарілих плоских файлів `output/<stem>.<ext>` не потрібна (або вони просто ігноруються сканером версій у `output/<stem>/`); проєкт перебуває на етапі активної локальної розробки.
- Деревоподібне візуальне відображення гілок (DAG-граф версій) не потрібне: усі версії відображаються лінійним хронологічним списком `Оригінал`, `v001`, `v002`, …, де нова операція з будь-якої основи просто додає наступний номер `v(max+1)`.
- Збереження Undo-стеку між повними перезапусками процесу воркера не потрібне (достатньо сесійного стеку у `StudioPipeline`, тоді як самі файли версій та `.studio_meta.json` зберігаються на диску).

## Decisions

### 1. Структура папок у `output/` та персистентність активної версії
- **Рішення**: Для кожного оригінального файлу `<stem>.<ext>` у `working_dir` створювати папку `output/<stem>/`. Усередині неї версійні файли іменуються суворо за шаблоном `<stem>-v{num:03d}.{ext}` (розпізнаються регулярним виразом `^<re.escape(stem)>-v(\d+)\.<ext>$`). Поточна активна версія зберігається у прихованому файлі `output/<stem>/.studio_meta.json` (`{"active_version_id": "v002"}` або `"original"`).
- **Альтернативи**:
  - *Зберігати активну версію лише в пам'яті фронтенда/воркера*: при оновленні сторінки або `list_files` вибір активної версії втрачався б.
  - *Один глобальний `manifest.json` у `output/`*: створює гонку записів при паралельному CPU-пакеті (`ThreadPoolExecutor` для `crop`/`resize`). Локальний `.studio_meta.json` у папці кожного `<stem>/` ізольований на рівні окремого файлу й ігнорується всіма сканерами зображень завдяки префіксу `.`.
- **Fallback**: Якщо `.studio_meta.json` відсутній або вказує на видалену версію, воркер автоматично обирає останню наявну версію `vNNN` (найбільший номер), а якщо версій не залишилося — `"original"` і видаляє порожню папку `output/<stem>/`.

### 2. Семантика `is_processed`, `has_outputs` і `active_version_id`
- **Рішення**: Розділити два поняття в `StudioFileEntry`:
  - `active_version_id: str` — версія, з якою користувач працює зараз (`"original"` або `"vNNN"`).
  - `is_processed: bool` — `True`, коли `active_version_id != "original"` (активна версія — оброблена; полотно показує слайдер «До / Після», мінімапу активної версії, а на полотні активні кнопки `Download` і `Restore`).
  - `version_count: int` — загальна кількість версій (`1 + кількість vNNN`), `has_outputs: bool` (`version_count > 1`).
  - На рівні списків та пакетних дій: `processed_count` рахує файли з `has_outputs == True` (щоб зелена галочка у Project Folder та кнопки `Download All` / `Restore All` залишалися доступними, навіть якщо користувач тимчасово перемкнув активний файл на `Оригінал` для нової гілки обробки), а `total_output_versions` передає загальну кількість файлів у `output/*/*`.
- **Альтернативи**: Прив'язати `Download All` / `Restore All` лише до `is_processed` змусило б кнопки зникати, коли користувач узяв `Оригінал` у роботу при збережених `v001..v003`. Окреме поле `has_outputs` / `total_output_versions` усуває цю колізію.

### 3. Нумерація версій та видалення довільних версій
- **Рішення**: Новий номер при збереженні завжди обчислюється як `max(existing_nums, default=0) + 1`.
  - Якщо існують `v001`, `v002`, `v003` і видаляється `v002`, наступна операція створить `v004` (без перезапису `v003`).
  - Якщо через `Undo` або видалення прибирається остання `v003`, залишаються `v001`, `v002`, і наступна операція чисто створить `v003`.
- **Альтернативи**: Окремий лічильник `next_version` у `.studio_meta.json` призводив би до «дірок» у нумерації після кожного `Undo`. Обчислення `max + 1` від фактичних файлів на диску просте, надійне й виключає колізії.

### 4. Розширення zero-copy RPC та мініатюри для popup-списку версій
- **Рішення**:
  - `studio.list_files`: повертає `StudioFileEntry` із масивом `versions: List[StudioVersionEntry]` (метадані всіх версій без важких бінарників), `active_version_id`, `version_count`, `has_outputs`, `can_undo` та `total_output_versions`, а бінарний payload містить лише по одній мініатюрі на файл (для поточної активної версії).
  - Новий опкод `studio.get_version_thumbnails` (`{ filename }` → zero-copy packed WebP-мініатюри `240×240` для всіх версій цього файлу): викликається ліниво при відкритті `#version-popup` для конкретного файлу, щоб навіть за 20+ версій не декодувати десятки повнорозмірних зображень у пам'яті браузера.
  - `studio.get_image`: отримує опційний `version_id: Optional[str] = None`; без нього повертає `original` + поточну `active_version_id` (сумісно з полотном «До / Після»), а з `version_id` — байти конкретної версії (для скачування чи повного перегляду).
  - Нові опкоди керування: `studio.select_version`, `studio.delete_version`, `studio.undo`.
  - Після редагування `worker.py` обов'язково перегенеровується `src/jetpack-env.d.ts` через `jetpack codegen`.

### 5. Багатокроковий стек `Undo` на бекенді
- **Рішення**: `StudioPipeline` веде поточний стек `self._undo_stack: List[UndoAction]` (захищений `threading.Lock()`). Кожен виклик `process_file` (одиночний) або `process_batch` (`Process All`) формує один `UndoAction`, що містить:
  - список `UndoItem(filename, created_version_id, created_path, previous_active_version_id)` для кожного обробленого в цій дії файлу, і `tool`.
  - При виклику `studio.undo`:
    1. Дістається верхній `UndoAction`.
    2. Для кожного `UndoItem` видаляється `created_path` (якщо існує на диску), видаляється порожня папка `output/<stem>/` (разом з `.studio_meta.json`), а якщо версії ще залишилися — `active_version_id` відновлюється на `previous_active_version_id` (або найближчий валідний fallback, якщо попередню версію вже видалили вручну).
  - При `studio.delete_version` або `studio.restore`:
    - `restore_all` очищує `_undo_stack`.
    - `restore_file(filename)` прибирає записи для `filename` зі стеку (і порожні `UndoAction`).
    - `delete_version(filename, vid)` прибирає відповідний `UndoItem` зі стеку (щоб `Undo` не спрацьовував вхолосту на вже видалену вручну версію).

### 6. UI-розміщення кнопки `Undo` та UX popup-меню версій
- **Рішення**:
  - У `index.html` в `.control-strip-left` одразу після зеленої групи `Process` / `Process All` (і перед групою `Restore All` / `Download All`) додається іконкова кнопка `#btn-undo` без тексту (`class="btn btn-ghost btn-icon"`) із чіткою SVG-іконкою стрілки скасування (`undo` — загнута вліво стрілка, візуально відмінна від кругової стрілки `Restore All`) та `title="Скасувати останню дію (Undo)"`.
  - У `#version-popup` рендеряться картки **усіх** версій у порядку зростання (або оригінал зверху + `v001`, `v002`, … знизу з автоскролом або компактною висотою картки, щоб комфортно переглядати багато версій). Кожна картка використовує свій URL мініатюри (`versionThumbUrls`), отриманий через `studio.get_version_thumbnails` (та кешований до зміни/видалення версії).
  - Кнопки кожної картки:
    - «Взяти в роботу» (`studio.select_version`, активна або підсвічена для поточної робочої версії) — оновлює активну версію файлу, полотно та розміри `Crop` / `Resize`, не закриваючи або оновлюючи стан без втрати історії.
    - «Скачати» (`studio.get_image` із `version_id` або `variant="original"`) — завантажує конкретну версію з точним іменем файлу (`my-image-1-v001.jpg`).
    - «Видалити» (`studio.delete_version`) — вимкнена для `original`, активна для будь-якої `vNNN`.

## Risks / Trade-offs

- **Колізія імен папок при однакових `stem` із різними розширеннями (наприклад, `photo.jpg` та `photo.png` в одному workspace)** → Таке саме обмеження існувало й раніше в `find_output_file(orig_path.stem)`. Документуємо як відоме обмеження поточного ключування за `stem` (можливе розширення у майбутньому через `<filename>` або суфікс).
- **Пам'ять браузера при перегляді великої кількості версій** → Мініатюри для `#version-popup` стискаються у WebP `240×240` і завантажуються лише при відкритті popup для конкретного файлу, а старі ObjectURL відкликаються при закритті/видаленні/відновленні.
- **Синхронізація кешу прев'ю на полотні після `Undo`, `Delete` або `Select Version`** → При будь-якій з цих мутацій `StudioController` інвалідує `previewCache` для змінених файлів і перезавантажує активне прев'ю, а `resolveViewfinderImageState()` та `renderCanvas()` включають `active_version_id` / `outputUrl` у `lastCanvasRenderKey`, щоб полотно і мінімапа миттєво перебудовувалися.
